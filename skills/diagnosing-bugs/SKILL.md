# 诊断 Bug

这是一套处理棘手 bug 的纪律。只有在明确说明理由时才跳过阶段。

探索代码库时，读取 `CONTEXT.md`（如果存在）以建立相关模块的清晰心智模型，并检查你要触碰区域的 ADR。

## 阶段 1：建立反馈循环

**这就是这个 skill 的核心。** 其他一切都是机械动作。如果你有一个针对该 bug 的**紧密**通过/失败信号，也就是会因为_这个_ bug 变红的信号，你就能找到原因；二分、假设验证和插桩都只是消费这个信号。如果没有，再怎么盯着代码看也救不了你。

在这里投入不成比例的精力。**要强硬。要有创造力。拒绝放弃。**

### 构造反馈循环的方法，大致按这个顺序尝试

1. **失败测试**：放在任何能触达 bug 的 seam 上，可以是 unit、integration、e2e。
2. **Curl / HTTP 脚本**：针对正在运行的 dev server。
3. **CLI 调用**：使用 fixture 输入，将 stdout 与已知正确快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，断言 DOM/console/network。
5. **回放捕获的 trace。** 将真实网络请求 / payload / event log 保存到磁盘；在隔离环境中通过代码路径回放。
6. **一次性 harness。** 启动系统的最小子集（一个服务、mock 依赖），用一个函数调用触发 bug 代码路径。
7. **Property / fuzz 循环。** 如果 bug 是“有时输出错误”，运行 1000 个随机输入并寻找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态（commit、dataset、version）之间，自动化“在状态 X 启动、检查、重复”，这样就能 `git bisect run`。
9. **差分循环。** 将同一输入跑过旧版本与新版本（或两套配置），并 diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人点击，用 `scripts/hitl-loop.template.sh` 驱动_人_，让循环仍然结构化。捕获到的输出反馈给你。

建立正确的反馈循环，bug 就已经修好了 90%。

### 收紧循环

把这个循环当成产品。一旦你有了_一个_循环，就**收紧**它：

- 我能让它更快吗？（缓存设置、跳过无关初始化、缩小测试范围。）
- 我能让信号更尖锐吗？（断言具体症状，而不是“没有崩溃”。）
- 我能让它更确定吗？（固定时间、固定 RNG 种子、隔离文件系统、冻结网络。）

一个 30 秒且 flaky 的循环只比没有循环好一点点；一个 2 秒且确定的循环才是紧密的调试超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。将触发器循环 100 次、并行化、增加压力、缩小计时窗口、注入 sleep。50% 的 flaky bug 可以调试；1% 不行。持续提高复现率，直到它可调试。

### 当你确实无法建立循环

停下来并明确说明。列出你尝试过的东西。向用户请求：(a) 能复现问题的环境访问权限，(b) 捕获的制品（HAR 文件、日志转储、core dump、带时间戳的屏幕录制），或 (c) 添加临时生产插桩的许可。**不要**在没有循环的情况下继续猜测。

### 完成标准：一个紧密且会变红的循环

阶段 1 在循环同时满足**紧密**和**可变红**时完成：你能说出**一条命令**，可以是脚本路径、测试调用或 curl；你已经**至少运行过一次**（粘贴调用及其输出），并且它满足：

- [ ] **可变红**：它驱动真实 bug 代码路径，并断言**用户描述的确切症状**，因此会因为这个 bug 变红、修好后变绿。不是“运行时不报错”，它必须能_抓住这个具体 bug_。
- [ ] **确定性**：每次运行结论相同（flaky bug：如上所述，固定且高复现率）。
- [ ] **快速**：以秒计，而不是分钟。
- [ ] **代理可运行**：你可以无人值守地运行；人只通过 `scripts/hitl-loop.template.sh` 参与循环。

如果你发现自己在这条命令存在之前就开始读代码构建理论，**停下：直接跳到假设正是这个 skill 要防止的失败。** 没有可变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

运行循环。看它变红，也就是 bug 出现。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是附近的另一个失败。错 bug = 错修复。
- [ ] 失败在多次运行中可复现（或对非确定性 bug 来说，复现率足够高，可以据此调试）。
- [ ] 你已经捕获了确切症状（错误信息、错误输出、慢时序），因此后续阶段可以验证修复确实解决它。

### 最小化

一旦它变红，就将复现缩小到**仍然会变红的最小场景**。一次只裁掉一个输入、调用方、配置、数据或步骤，并在每次裁剪后重新运行循环，只保留对失败承重的部分。

为什么要费这个劲：最小复现会缩小阶段 3 的假设空间（剩下要怀疑的移动部件更少），并在阶段 5 成为干净的回归测试。

当**每个剩余元素都是承重的**时完成：移除其中任何一个都会让循环变绿。

在你已经复现**并且**最小化之前，不要继续。

## 阶段 3：提出假设

在测试任何假设之前，生成 **3–5 个按优先级排序的假设**。只生成一个假设会把你锚定在第一个貌似合理的想法上。

每个假设都必须是**可证伪的**：说明它做出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更糟。”

如果你无法说出预测，这个假设只是一种感觉：丢弃它或把它磨尖。

**在测试之前，把排序后的列表展示给用户。** 他们常常有能立刻重排的领域知识（“我们刚部署了 #3 的相关改动”），或知道哪些假设已经被排除。这个检查点成本很低，却非常省时间。不要卡住等待；如果用户不在，就按你的排序继续。

## 阶段 4：插桩

每个探针都必须映射到阶段 3 中的某个具体预测。**一次只改变一个变量。**

工具偏好：

1. 如果环境支持，优先使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能区分假设的边界处放**定向日志**。
3. 永远不要“把所有东西都 log 出来再 grep”。

**给每条 debug 日志打唯一前缀**，例如 `[DEBUG-a4f2]`。最后清理会变成一次 grep。未打标签的日志会幸存；打标签的日志必须消失。

**性能分支。** 对性能回归，日志通常是错的。改为先建立基线测量（计时 harness、`performance.now()`、profiler、query plan），再二分。先测量，再修复。

## 阶段 5：修复 + 回归测试

在修复之前先写回归测试，但前提是存在**正确的 seam**。

正确的 seam 是指测试能像调用点实际发生的那样，覆盖**真实 bug 模式**。如果唯一可用 seam 太浅（例如 bug 需要多个调用方，而你只有单调用方测试；或 unit test 无法复现触发 bug 的调用链），在那里的回归测试会给出虚假的信心。

**如果不存在正确 seam，这本身就是发现。** 记录下来。代码库架构正在阻止这个 bug 被锁定。把这一点标记给下一阶段。

如果存在正确 seam：

1. 将最小复现转成该 seam 上的失败测试。
2. 看它失败。
3. 应用修复。
4. 看它通过。
5. 针对原始（未最小化）场景重新运行阶段 1 的反馈循环。

## 阶段 6：清理 + 复盘

在声明完成前必须做到：

- [ ] 原始复现不再复现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或已记录缺少 seam）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 该前缀）
- [ ] 一次性原型已删除（或移动到清晰标记的调试位置）
- [ ] 在 commit / PR message 中说明最终被证实的假设，让下一位调试者能学到东西

**然后问：什么本可以防止这个 bug？** 如果答案涉及架构变更（没有好的测试 seam、调用方纠缠、隐藏耦合），带着具体信息交给 `/improve-codebase-architecture` skill。这个建议要在修复完成之后提出，而不是之前：现在你比刚开始时知道得更多。
