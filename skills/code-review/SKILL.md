对用户提供的固定点与 `HEAD` 之间的 diff 做双轴审查：

- **标准**：代码是否符合本仓库已记录的编码标准？
- **规格**：代码是否忠实实现了原始 issue / PRD / spec？

两个轴线都作为**并行子代理**运行，这样它们不会污染彼此的上下文；随后本 skill 汇总它们的发现。

issue tracker 应该已经提供给你；如果缺少 `docs/agents/issue-tracker.md`，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定比较点

用户说的任何内容都是固定点：commit SHA、branch 名、tag、`main`、`HEAD~5` 等等。如果用户没有指定，就询问。

只记录一次 diff 命令：`git diff <fixed-point>...HEAD`（三点语法，因此比较对象是 merge-base）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录 commit 列表。

继续之前，确认固定点可以解析（`git rev-parse <fixed-point>`），并且 diff 非空。错误的 ref 或空 diff 应该在这里失败，而不是在两个并行子代理内部失败。

### 2. 识别规格来源

按以下顺序寻找原始规格：

1. commit message 中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）：通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 PRD/spec 文件。
4. 如果什么都没找到，询问用户规格在哪里。如果用户说没有规格，**规格**子代理将跳过，并报告“没有可用规格”。

### 3. 识别标准来源

仓库中任何记录代码应该如何编写的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库已有文档之外，标准轴线始终携带下面的**异味基线**：一组固定的 Fowler 代码异味（_Refactoring_ 第 3 章），即使仓库没有记录任何标准也适用。它受两条规则约束：

- **仓库规则优先。** 已记录的仓库标准总是胜出；如果仓库认可了基线会标记的做法，就抑制该异味。
- **始终是判断题。** 每个异味都是带标签的启发式判断（“可能的 Feature Envy”），从来不是硬性违规；并且，和这里的任何标准一样，跳过工具已经强制执行的内容。

每个异味按“它是什么”→“如何修复”阅读；将它与 diff 对照：

- **Mysterious Name**：函数、变量或类型的名称没有揭示它做什么或承载什么。→ 重命名；如果找不到诚实的名称，说明设计不清晰。
- **Duplicated Code**：同样的逻辑形状出现在变更中的多个 hunk 或文件里。→ 提取共享形状，并从两处调用。
- **Feature Envy**：一个方法访问另一个对象的数据多于访问自己的数据。→ 把这个方法移动到它“羡慕”的数据所在对象上。
- **Data Clumps**：同几组字段或参数总是一起传递（一个类型想要诞生）。→ 把它们打包成一个类型，并传递这个类型。
- **Primitive Obsession**：用 primitive 或 string 代表一个值得拥有自身类型的领域概念。→ 给这个概念一个小类型。
- **Repeated Switches**：针对同一类型的相同 `switch`/`if` 级联在变更中重复出现。→ 用多态替换，或让两处共享同一个 map。
- **Shotgun Surgery**：一个逻辑变更迫使 diff 中许多文件分散修改。→ 把一起变化的东西收拢到一个模块里。
- **Divergent Change**：一个文件或模块因为多个无关原因被编辑。→ 拆分它，让每个模块只因一个原因变化。
- **Speculative Generality**：为了规格中并不存在的需求添加抽象、参数或 hook。→ 删除它；内联回去，直到出现真实需求。
- **Message Chains**：调用方不该依赖的长链式导航 `a.b().c().d()`。→ 在第一个对象上用一个方法隐藏这段遍历。
- **Middle Man**：一个类或函数大部分只是继续委托。→ 去掉它，直接调用真实目标。
- **Refused Bequest**：子类或实现者忽略或覆盖了它继承的大部分内容。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

发送一条包含两个 `Agent` 工具调用的消息。两个都使用 `general-purpose` 子代理。

**标准子代理提示**：包含：

- 完整 diff 命令和 commit 列表。
- 第 3 步找到的标准来源文件列表，**再加上第 3 步的异味基线全文**：子代理无法通过其他方式访问它。
- 简报：“报告：在相关文件/hunk 级别指出 (a) diff 违反已记录标准的每一处：引用该标准（文件 + 规则）；以及 (b) 你发现的任何基线异味：说出名称并引用 hunk。区分硬性违规和判断题：已记录标准的违反可以是硬性问题，但基线异味始终是判断题，且已记录的仓库标准优先于基线。跳过工具已经强制执行的内容。400 字以内。”

**规格子代理提示**：包含：

- diff 命令和 commit 列表。
- 规格路径或获取到的规格内容。
- 简报：“报告：(a) 规格要求但缺失或只部分实现的需求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看似已实现但实现看起来错误的需求。每条发现都引用规格行。400 字以内。”

如果缺少规格，跳过规格子代理，并在最终报告中说明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下展示两份报告，原样或轻微清理。**不要**合并或重新排序发现；这两个轴线是刻意分开的（见 _Why two axes_）。

最后用一行总结：每个轴线的发现总数，以及每个轴线内部最严重的问题（如果有）。不要在两个轴线之间选一个单一赢家，那正是这种分离要避免的重新排序。

## 为什么是两个轴线

一个变更可能通过一个轴线却失败在另一个轴线：

- 代码遵守所有标准，但实现了错误的东西 → **标准通过，规格失败。**
- 代码完全符合 issue 要求，但破坏了项目约定 → **规格通过，标准失败。**

分开报告可以避免一个轴线遮蔽另一个轴线。
