# 测试驱动开发

TDD 是 red → green 循环。这个 skill 是让该循环产出值得保留的测试的参考：什么是好测试、测试放在哪里、反模式，以及循环规则。每个循环都适用每一节：在循环前和循环中查阅它们，而不是事后。

探索代码库时，读取 `CONTEXT.md`（如果存在），让测试名称和接口词汇符合项目的领域语言，并尊重你要触碰区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以完全改变；测试不应该。好测试读起来像一份规格：“user can checkout with valid cart” 精确说明了存在什么能力，并且因为不关心内部结构，所以能经受重构。

示例见 [tests.md](tests.md)，mocking 指南见 [mocking.md](mocking.md)。

## Seams：测试放在哪里

**seam** 是你测试的公共边界：你可以在不伸手进入内部的情况下观察行为的接口。测试只存在于 seams 上，绝不针对内部。

**只在预先约定的 seams 上测试。** 写任何测试之前，写下将被测试的 seams，并与用户确认。未经确认的 seam 上不写测试。你无法测试一切；提前约定 seams，是为了让测试精力落在关键路径和复杂逻辑上，而不是每个边角。

问：“公共接口是什么？我们应该测试哪些 seams？”

## 反模式

- **耦合实现**：mock 内部协作者、测试 private methods，或通过 side channel 验证（查询数据库而不是使用接口）。识别信号：重构时测试失败，但行为没有改变。
- **同义反复**：断言用与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、用同样方式手工推导 snapshot、断言一个常量等于自身），因此测试按构造必然通过，永远不会与代码产生分歧。期望值必须来自独立真相来源：已知正确的 literal、推演过的例子、spec。
- **水平切片**：先写所有测试，再写所有实现。批量测试验证的是_想象中的_行为：你测试的是事物的_形状_而不是面向用户的行为，测试对真实变化变得不敏感，并在理解实现之前就承诺测试结构。改用**垂直切片**：一个测试 → 一个实现 → 重复，每个测试都是一颗**曳光弹**，会响应上一个循环教给你的东西。

## 循环规则

- **先红后绿。** 先写失败测试，然后只写足够让它通过的代码。不要预判未来测试或添加推测性功能。
- **一次一个切片。** 每个循环只处理一个 seam、一个测试、一个最小实现。
- **重构不是循环的一部分。** 它属于 review 阶段（见 `code-review` skill），不属于 red → green 实现循环。
