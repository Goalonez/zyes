# ADR 格式

ADR 存放在 `docs/adr/`，并使用连续编号：`0001-slug.md`、`0002-slug.md` 等。

懒创建 `docs/adr/` 目录：只有在第一个 ADR 被需要时才创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么，我们决定了什么，以及为什么。}
```

就是这样。一个 ADR 可以只有一个段落。价值在于记录*做出了*某个决策以及*为什么*，而不是填满各个章节。

## 可选章节

只有在真正增加价值时才包含这些内容。大多数 ADR 不需要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：在重新审视决策时有用
- **Considered Options**：只有当被拒绝的替代方案值得记住时
- **Consequences**：只有当非显而易见的下游影响需要指出时

## 编号

扫描 `docs/adr/`，找到已有最高编号并加一。

## 何时提出 ADR

以下三点必须全部为真：

1. **难以反转**：以后改变主意的成本有实际意义
2. **没有上下文会令人意外**：未来读者看着代码会疑惑“他们到底为什么要这样做？”
3. **真实权衡的结果**：确实存在可行替代方案，而你基于具体原因选择了其中一个

如果一个决策很容易反转，就跳过它：到时候你会直接反转。如果它不令人意外，没人会疑惑为什么。如果没有真实替代方案，除了“我们做了显而易见的事”之外没什么可记录。

### 哪些内容符合条件

- **架构形状。** “我们使用 monorepo。”“写模型是 event-sourced，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “Ordering 和 Billing 通过 domain events 通信，而不是同步 HTTP。”
- **带来锁定效应的技术选择。** 数据库、消息总线、认证提供商、部署目标。不是每个库，只是那些替换起来要花一个季度的东西。
- **边界和范围决策。** “Customer 数据由 Customer context 拥有；其他上下文只通过 ID 引用它。” 明确的 no 和 yes 一样有价值。
- **有意偏离显而易见路径。** “我们使用手写 SQL 而不是 ORM，因为 X。” 任何合理读者会默认相反的地方都算。这些记录能阻止下一位工程师去“修复”其实是刻意为之的东西。
- **代码里看不见的约束。** “因为合规要求，我们不能使用 AWS。”“因为合作伙伴 API 合约，响应时间必须低于 200ms。”
- **拒绝非显而易见的替代方案。** 如果你考虑过 GraphQL，并因为微妙原因选择了 REST，就记录下来；否则六个月后还会有人再次建议 GraphQL。
