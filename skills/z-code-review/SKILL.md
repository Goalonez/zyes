# 审查代码改动

## 确定范围

使用调用方指定的 diff、提交或改动范围。未指定时，检查当前工作区的暂存、未暂存改动及未跟踪文件；范围仍不明确时询问调用方。

结合调用方提供的需求、约束和已有验证结果建立上下文。独立调用时，从相关代码和项目文档中核实这些依据，按指定范围直接审查。

## 审查

- 沿改动读取必要的调用方、配置和测试，核实入口、信任边界、契约与实际影响。
- 以满足当前需求的最小充分实现为标准，重点检查缺少当前需求依据的抽象与分层、多层透传、重复逻辑和多余中间状态。
- 检查同一信任边界内重复校验已由明确契约保证的条件，以及缺少具体风险依据的防御、兼容和兜底分支；核实本次改动造成的失效路径与残留实现。
- 同时检查正确性、安全边界、行为回归和关键验证缺口。复用仍然有效的验证结果，证据不足时按需补充针对性检查。

## 核实问题

仅报告有依据、可行动的问题。判断结构是否必要，应结合实际职责、调用方式和项目惯例，而非单凭代码长度、实现数量或个人风格。

对简化建议，说明多余之处、具体依据和最小调整方向，核实简化后仍满足需求、行为契约与必要的安全边界。校验是否重复应覆盖相关入口及其信任边界。依据不足时标为待确认疑点。

## 输出

默认直接在对话中输出审查结论，按影响和处理优先级列出问题，给出文件位置、依据、触发条件或多余之处及其影响，简述必要的修复或简化方向。区分确认的问题与待确认的疑点，说明审查范围、未验证项和判断边界。

没有发现可行动的问题时，明确说明。修复与简化由调用方处理；由 z-implement 调用时，返回结论供其继续实施、验证和复查。
